# Glyph app UI audit — 2026-10-23

Reviewed commit `f7a157f` on `feat/dpower-core`. This is a source-based interaction/status audit, including Android layout XML and the existing lint report. No phone is connected; no rendered screen, physical Glyph readability, gesture comfort, TalkBack session or font-scale test is claimed. Findings below describe the original baseline. The follow-up implementation is recorded in [functional fixes](functional-fixes-2026-10-23.md).

The Nothing Glyph Matrix is the play surface. The phone UI should make it easy to load a device, understand whether it is running on Glyph, learn its controls and manage saves.

## Prioritised findings

### 1. High — ROM header stays stale after import

`RomLoaderActivity.kt:619` calls `updateStatus()` during creation. There are no later callers. The new asynchronous import at `1558–1594` starts the service and shows a toast; its completion never refreshes the header. `onResume:625` only starts preview polling, and that polling does not call `updateStatus` either.

A user can import D-Power while the screen continues to name the old classic ROM or say no ROM is loaded. Save rows meanwhile read the new files, making the screen internally inconsistent. This is a regression introduced by the new import flow.

**Fix:** publish an import result with request ID and selected device identity, and refresh all device-dependent UI together after success. Preserve the previous identity during pending/failed import. A toast alone is not a durable result.

### 2. High — “ACTIVE/IDLE” is not emulator or Glyph status

`RomLoaderActivity.kt:764–771` infers ACTIVE from a frame younger than two seconds. `EmulatorLoop.kt:190–194` publishes only when display generation changes. A running pet with an unchanged LCD therefore becomes IDLE. Conversely, preview activity does not establish that a frame reached the Nothing display: `GlyphRenderer.kt:25–44` silently catches SDK/disconnection failures.

**Fix:** expose separate runtime state (running / frozen / stopped / error) and Glyph connection/output state. Keep “last frame changed” as optional diagnostic information. Do not use frame age as a CPU heartbeat or connection indicator.

### 3. High — destructive reset is a one-tap action with unclear consequences

`RomLoaderActivity.kt:397–399` posts full reset immediately. `DigimonGlyphToyService.kt:1251–1267` resets the machine and overwrites its autosave. The button says HARD RESET, but does not explain that the current pet and autosave are replaced. Manual-slot loading can likewise rewind progress without explaining the selected save's time/device at the point of action.

**Fix:** use “Reset this pet” with a confirmation naming the active device and autosave consequence. Offer a manual backup before reset. For loading, show slot/device/time clearly and explain the rewind. This recommendation concerns the product's user interaction, not permission for coding changes.

### 4. Medium — device capabilities are not reflected in available controls

The D-Power controls button is visible for classic ROMs, then refuses the click (`RomLoaderActivity.kt:1596–1604`). The battle section, care alerts, care-mistake option, A/B/C macros and classic tutorial remain available on D-Power. Opening battles can demand a tamer alias before the backend eventually says battles are unavailable (`450–458`, `637–659`; service `startBattleHost/startBattleJoin`). `activity_tutorial.xml:95` still gives classic hatching/care instructions.

**Fix:** derive visible/enabled features and help from the selected device's capabilities. Show D-Power gestures and manual Step/Card controls for D-Power; classic care/evolution/battle tools for validated classic devices. Where a feature is planned but unavailable, explain that before the user starts configuring it. Do not reinterpret classic A/B/C macros as supported D-Power actions.

### 5. Medium — display/timing settings promise behaviour they do not control

The “FULL ACCURACY MODE (MAX BATTERY USE)” switch (`activity_rom_loader.xml:384`) changes the render cadence and execution batch size; both modes retain real-time CPU scheduling. It invites users with clock drift to treat it as a clock-accuracy fix.

D-Power always selects full-width fit (`DisplayBridge.kt:123`), even though AUTO ZOOM-OUT LOGIC remains an enabled toggle (`RomLoaderActivity.kt:360–364`). Changing it cannot affect D-Power rendering.

**Fix:** label the former “Smoother display” with 15/30 FPS explained briefly. For D-Power, show “Full LCD fitted to Glyph” and disable/hide the classic auto-fit toggle, or implement an explicit device-appropriate view choice. Explain that fitting reduces horizontal detail; verify actual text on the hardware before calling it readable.

### 6. Medium — archive import has no visible pending state or cancellation

Scanning runs on a raw Thread (`RomLoaderActivity.kt:1558–1576`) and can process up to 256 MB of decompressed data. Until scanning ends, there is no progress state; repeated requests can start overlapping scans. A destroyed activity drops successful results, while error callbacks are not similarly guarded. The UI's only pending message starts after selection/staging, not during archive scanning.

**Fix:** use a lifecycle-aware import state: scanning, choosing, saving current pet, switching, success or failure. Disable duplicate submissions, allow cancelling scanning, and keep errors visible next to the ROM controls. Request IDs should prevent late results from replacing the newest choice.

### 7. Medium — main-thread polling rereads and hashes the ROM roughly eight times per second

`debugRefresh:102–105` runs every 120 ms. Each `renderDebugState` invokes `refreshSaveAndCommandInfo:1275`, which calls `readCurrentRomIdentity:1326` and reads/hashes the entire ROM on the main thread. This occurs even when save tools are collapsed. At D-Power's 96 KiB size, that is approximately 0.78 MiB/s of repeated reading plus SHA-256/string allocation without a device change. This is source-confirmed redundant work; frame drops/battery impact were not profiled.

**Fix:** cache identity on ROM load/switch, update save rows on save/load acknowledgements, and throttle debug refresh separately from normal UI. Do not make a UI refresh interval responsible for device discovery.

### 8. Medium — D-Power control help is ambiguous and the dialog can overflow

The new dialog (`RomLoaderActivity.kt:1605–1620`) explains “positive” and “negative” flicks, which are sensor conventions rather than user instructions. It packs help plus six buttons into a non-scrollable LinearLayout. Small screens, landscape or enlarged fonts may hide lower controls; this is a layout risk awaiting rendered verification. The dialog also offers no indication that a button was ignored because DND Freeze is active.

**Fix:** provide a scrollable, device-specific control guide with physical direction diagrams, explicit hold-and-flick sequences and input feedback. Validate direction labels on the actual phone. Keep secondary screen controls compact, and show paused/frozen status next to them.

### 9. Low — visual language and accessibility need a focused pass

Core actions are labelled MOUNT ROM ARCHIVE, EXECUTE, TERMINATE, SOFT REBOOT and HARD RESET. These obscure ordinary operations such as Load ROM, Start, Stop, Restart and Reset pet. The visual style can remain while the action labels become plain. Correction after follow-up: the six 44 dp icons are decorative ImageViews, with clickable/focusable disabled, not buttons. The real density defect was raw-pixel dimensions in manual-save row buttons, now fixed. New dialog strings are hardcoded English and its padding is in raw pixels.

**Fix:** move product strings into resources, use density-independent dimensions, verify focus order/content descriptions and enlarged text, and retain technical registers/transport settings inside an explicitly advanced area.

## Recommended change order

1. Create one observable device/runtime/import state; fix stale identity and separate running from Glyph-connected status.
2. Make controls, settings and help device-aware. Remove redundant ROM reads from the refresh loop.
3. Clarify reset/load consequences and add durable command/import feedback.
4. Refine the existing layout into device + Glyph status, primary actions, controls/help, saves, then optional advanced tools. No wholesale visual rebrand is required.
5. Verify on a Nothing Phone: classic → D-Power → classic import; static LCD; screen-off; Glyph disconnect/rebind; DND Freeze; failed/cancelled import; save/restore/reset; large fonts; all six gestures and LCD menu text.

## What already works structurally

The app sends 25×25 frames to Glyph, offers explicit selection for multi-ROM archives, identifies known dumps by hash, and isolates saves by hash. D-Power firmware, controls and snapshot behaviour have local tests. Those are useful foundations, but build/lint success is not a substitute for this interaction and hardware review.
